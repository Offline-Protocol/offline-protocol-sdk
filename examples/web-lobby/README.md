# Pong lobby

A two-player Pong game between browsers, with no server. Each browser runs a full Offline Protocol node in a Web Worker with durable storage. The host makes an MLS group and invites every device it forms a session with; the host's game state goes to the group ten times a second, end-to-end encrypted, and the other player sends its paddle back as a direct message.

```bash
cargo install wasm-bindgen-cli --version 0.2.105 --locked   # once; must match Cargo.lock
bash bindings/web/scripts/build.sh
python3 -m http.server 8000 --bind 0.0.0.0                   # from the repository root
```

**Two devices on one network.** Open `http://<this-machine>:8000/examples/web-lobby/` on both. A browser gives WebRTC and OPFS only to a secure context, and a LAN address over plain HTTP is not one, so serve the page over HTTPS, or on a phone use a tunnel to `localhost`. On one device press **Host a game**, then **Connect a device: make a code**, and get the code to the other device (paste it, or show it as a QR code). The other device presses **I have a code**, pastes it, and sends its answer back the same way. The devices connect on the local network: no ICE server is configured, so nothing leaves it.

**Devices nearby, without codes.** Fill in the Nostr relays and the STUN server you want to use (the page names none, and remembers yours in this browser), a name to show, and press **Look for devices nearby** on each device. Every device behind the same public address appears in the list; press **Connect** beside one, and that device is asked whether to let it in. The relays carry only the setup, and the link runs on the local network. Anyone who can guess the network's address can see who is listed and ask to connect, which is why every request is asked about, and why the players list shows the address that actually joined ([docs/bridges/web.md](../../docs/bridges/web.md), W13).

**Two tabs of one browser.** Open <http://127.0.0.1:8000/examples/web-lobby/> and <http://127.0.0.1:8000/examples/web-lobby/?profile=b>. A durable node is one per account per origin, so the second tab needs its own profile. The tabs find each other over a `BroadcastChannel` with no codes.

The identity survives a reload: the same profile is the same `off1…` address, and still a member of the group.

**With no network at all.** Once opened online, the page loads offline: a service worker (`sw.js`) caches the page, the SDK and the engine module as one build, and a manifest lets the browser install it as an app. Two devices on a Wi-Fi network with no internet, or on a phone's hotspot, should still connect with two codes; CI checks the offline reload in three engines on one machine, and the phone run is step 9 of the [two-device checklist](../../docs/bridges/web-devices.md), not run yet. A new build shows **Update**: pressing it lets the new build take over, and then every open page with a running node stops it and reloads (a tab whose node was refused, or was still starting, asks you to reload it instead), because the page and its worker must run the same build ([W15](../../docs/bridges/web.md#w15-a-page-that-loads-offline-caches-one-build-whole)). Any change to a file the page loads (the page itself, or the SDK's JavaScript) needs `bash bindings/web/scripts/build-id.sh` before it is served, which names the cache and needs no Rust build (`build.sh` runs it too). Until then every device that opened the page keeps the cached copy, online included, so run it on a server after every pull, and publish `bindings/web/pkg/build-id.js` last when copying files to one (a browser that reads a new id beside old files caches the mix under it), and tick **Update on reload** in the developer tools while working on the page. Deleting `sw.js` does not remove it from a browser that has it: that browser keeps serving the cached page, online too. Leaving a checkout of this page for one without it, press **Unregister** for it in the developer tools (Application, Service workers); on a server, serve the retiring service worker in [W15](../../docs/bridges/web.md#w15-a-page-that-loads-offline-caches-one-build-whole) at the same URL.

Before a release, [docs/bridges/web-devices.md](../../docs/bridges/web-devices.md) is the checklist for running this page on a laptop and a phone.

**When a device goes away.** A phone that leaves the page, locks its screen or loses the network drops its link. Both pages say so: "connection unstable" while the browser still waits for an answer, then that the other device disconnected, with what to press to carry on. Two new codes bring it back with no second invite, as both devices are still in the group. A host that reloads comes back hosting the same game; **End this game** forgets it. A host that cannot add a device, or whose game updates stop reaching it, says why on screen.

The stats line shows what the game costs, including the durable store's flushes per second. The game state and the paddle are ephemeral sends: each goes once over the live link, is never acknowledged or retried, and is never held for a link that is down, so an update that missed its moment does not arrive late. On the browser's store that is two flushes per state for the host instead of four. See [docs/bridges/web.md](../../docs/bridges/web.md), W9 and W10.
