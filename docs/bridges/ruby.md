# Ruby binding contract

Covers `bindings/ruby`: the Ruby API generated from the interface definition,
for scripts, tooling and servers written in Ruby.

Read [the shared contract](README.md) first. This document covers what is
specific to Ruby.

## What it is

The Ruby binding is generated by UniFFI's own Ruby generator, from the same UDL
as Swift, Kotlin, Python and Java, and committed as one file,
`bindings/ruby/lib/offline_protocol.rb`. It is the fifth member of the artifact
set in [C1](README.md#c1-regenerate-every-binding-together). It calls the
native library through the `ffi` gem, not through
[the C API](c.md): there is no hand-written code in it at all, which is why
most of the rules below are about what the host owes.

The generated module is `OfflineProtocol`, and so is the engine class inside
it, so the engine is `OfflineProtocol::OfflineProtocol`. The generator offers
no way to rename the module: it ignores a `module_name` setting without a
warning.

## Which shared rules apply

| Rule | How it reaches the Ruby binding |
|---|---|
| [C1](README.md#c1-regenerate-every-binding-together) | Applies in full. `scripts/generate-bindings.sh` runs the Ruby generator with the other four, CI deletes and diffs `bindings/ruby/lib/offline_protocol.rb` with them, and `scripts/tests/test-generate-bindings.sh` pins the output path, the call and the config argument |
| [C2](README.md#c2-the-error-enum-is-append-only) | The generated `ProtocolError` and `MlsStorageError` decode by positional discriminant, like every other binding. Append-only keeps them correct |
| [C3](README.md#c3-events-cross-as-opaque-json) | `on_event` and `poll_event` deliver the engine's JSON. An event's fields appear in no Ruby type, and a field added to an event is invisible here until the host reads it |
| [C6](README.md#c6-config-parsers-must-not-default-to-literals) | Holds without a parser: the generated record carries the definition's own defaults. See R2 |
| [C9](README.md#c9-bridge-behaviour-is-not-covered-by-the-rust-test-suite) | `cargo test` proves nothing about this binding. `bundle exec rake test` in `bindings/ruby` runs the consumer check against the real library, and CI runs it on Linux, macOS and Windows |
| [C11](README.md#c11-a-storage-adapter-is-a-supported-extension-point-and-is-verified) | A protocol-state provider is an adapter like any other: `OfflineProtocol.run_storage_conformance` is the bar |
| [C12](README.md#c12-telemetry-is-callback-free-and-the-binding-fills-the-platform) | The exception. See R4 |

## R1. The library is loaded by the name the config gives it

The generated code opens the library by name, and the generator's default is
the UDL namespace (`uniffi_offline_protocol`), which no build of this repository
produces. `bindings/ruby/uniffi.toml` sets `cdylib_name` to the name the crate
builds, `offline_protocol_uniffi`, and `scripts/generate-bindings.sh` passes the
file. Only Ruby is given a config.

The generator ignores a setting it does not know without saying so, so a
misspelt key would produce a binding that fails with a `LoadError` for every
consumer and passes every generation check. The guard pins that the config is
passed, and the consumer check is what proves it took effect.

The generated code checks the library's FFI contract version and every
function's checksum when it loads, so a Ruby generated from a different
definition than the library fails at the first call, not at build time.

## R2. The generated records keep the definition's defaults

A dictionary field with a default in the UDL (`require_encryption = true`) is a
keyword argument with that default in the Ruby record, as in the Python one. A
caller names the fields the definition leaves without a default and omits the
rest. This is the opposite of [Java's J2](java.md#j2-the-generated-records-have-no-defaults),
and it is why Ruby needs no reference configuration to keep in step: the
default is generated, not copied.

## R3. An engine that is collected while it holds a callback leaks the callback

The generated engine class frees its Rust object from a garbage-collection
finalizer, and there is no other way to free it. Releasing a callback the
engine holds calls back into Ruby, and that code takes a lock, which Ruby
forbids inside a finalizer. The result, measured with Ruby 4.0.6 and UniFFI
0.32.2: an engine with no callback is freed cleanly, and an engine with an event
callback set leaves its callback registered for ever and prints
`can't be called from trap context` as a warning. In 200 engines each given a
callback, 166 callbacks stayed registered. The process does not crash.

The cost is a few objects per collected engine, so a host that keeps one engine
for the life of the process, which is how the engine is meant to be used, never
sees it. A host that builds and drops engines in a loop does. Keep the engine
reachable, and prefer `poll_event` to a callback where engines are short lived.
The consumer check keeps its engines in an array for this reason.

This is a defect in the generator, not something a Ruby wrapper can repair
without editing the generated file, which the drift gate forbids. Check it again
on a UniFFI bump.

## R4. The host fills the telemetry platform

Rule C12 says a binding fills `TelemetryConfig.os` and `os_major`, never the
app. There is no hand-written layer in the Ruby binding to do it, so the host
passes them, as the C binding's host passes `os_major`
([c.md K3](c.md#k3-the-binding-fills-the-telemetry-platform)). They must be the
platform the process actually runs on (`TelemetryOs::LINUX`, `MACOS`,
`WINDOWS`) and its major version, read from the host, and not a value forwarded
from configuration: the ingest keys its per-platform aggregates on them.

`every_bridge_reads_the_telemetry_config_section` has nothing to read for Ruby,
so nothing enforces this. A wrapper that adds a lifecycle should report
`notify_app_state` on backgrounding, and no call to `disable_telemetry`,
`end_telemetry_session` or `flush_telemetry_blocking` belongs on a thread that
must not block.

## R5. Callbacks are duck-typed, and the two storage providers take different bytes

A callback is any object that responds to the interface's methods, and the
generated code checks no type. The two storage interfaces differ only in how
they carry bytes, and the difference is not checked:

| Interface | `store` receives | `load` returns |
|---|---|---|
| Key material (`MlsStorageProvider`) | An `Array` of `Integer`, signed (R8) | An `Array` of `Integer` from 0 to 255, or `nil` |
| Protocol state (`ProtocolStateStorageProvider`) | A binary `String` | A binary `String`, or `nil` |

An adapter that returns the wrong one fails inside the library, not where it
was written. A failure is reported by raising a `MlsStorageError` variant; any
other exception reaches the engine as an unexpected error.

A callback runs synchronously, inside the engine, before the engine call that
produced it returns. The rules are
[the C binding's K2](c.md#k2-callbacks-run-on-the-engines-thread-inside-the-engine):
a callback must be safe from any thread, must not call back into the engine, and
must not raise anything but the interface's own error. Copy the event, queue it,
return. Storage providers are called from any thread, concurrently, so they must
be thread-safe.

## R6. Requirements the platform imposes

CI runs the consumer check on Ruby 4.0 on Linux, macOS and Windows, and on
Ruby 3.3 on Linux, which is the gemspec's `required_ruby_version`. The binding
needs the `ffi` gem (`~> 1.17`) and nothing else.

The native library is not bundled. The loader finds it on the library search
path: `LD_LIBRARY_PATH` on Linux, `DYLD_LIBRARY_PATH` on macOS, `PATH` on
Windows, or a system directory. RubyInstaller, the usual Ruby on Windows, takes
`PATH` out of the DLL search and reads `RUBY_DLL_PATH` instead, so set that one
there. The loader reads the variable when the process starts, so it has to
be set before Ruby launches, not by the program. On macOS a protected system
Ruby such as `/usr/bin/ruby` drops `DYLD_LIBRARY_PATH` at launch, so use a Ruby
you installed, or install the library in a directory the loader already
searches.

## R7. The gem is published to RubyGems, and does not carry the library

`offline_protocol` is the Ruby binding, published at the release's version by
`release.yml` under the `RUBYGEMS_PUBLISH` switch, with trusted publishing and
no stored credential. A prerelease such as `0.31.0-rc.1` is numbered the way
RubyGems numbers one, `0.31.0.pre.rc.1`.

The gem contains the generated binding, its README and the license notices.
It contains no native code, for the reason the Java jar does not
([J6](java.md#j6-the-jar-is-published-to-maven-central-and-does-not-carry-the-library)):
a gem that appeared to work and failed at the first call on a platform it did
not carry would be worse than one that says what it needs. The host supplies
the library for its platform from the release's desktop archives and puts it
on the loader's search path (R6).

The release tests the committed binding against the release profile's library,
builds the gem at the release's version, and checks it carries the binding and
the license before anything is pushed. A re-run of a release that already
reached RubyGems pushes nothing. `bundle exec rake build` builds the same gem,
and the Ruby Binding job in CI runs it on every pull request, so a gemspec
error shows there and not on a tag.

## R8. Bytes come back signed, and must be masked before they go back in

Every `u8` the library hands to Ruby, alone or in a `sequence<u8>`, arrives as
a signed value from -128 to 127: the generator reads it with a signed unpack
(`'c'`, not `'C'`). Bytes going the other way are range-checked as 0 to 255,
so a byte array taken from the engine and passed straight back, such as a key
package from `mls_get_or_create_key_package` given to
`send_connection_request`, raises `RangeError` before the call is made. Nothing
is corrupted: the engine never sees the refused call, and every value fits a
byte once masked.

Mask such an array with `map { |b| b & 0xFF }` before handing it on, or before
treating it as bytes (`pack("C*")` wraps a signed value correctly, which is why
the consumer check's key-material store works unmasked). The same applies to
the `data` an `MlsStorageProvider` receives in `store`. Byte arrays inside
event JSON are not affected: the JSON carries them as 0 to 255.

The defect is in the Ruby generator up to and including UniFFI 0.32.2, and in
its upstream main when this was written. The generated file cannot be patched
(the drift gate forbids it), so the host masks. The consumer check pins the
signed read: when a UniFFI bump fixes it, that test fails, and the mask in the
example and this section can go.

## What the host owes

The same things every binding owes, with nothing provided: the transports, two
storage providers or the built-in file stores, the lifecycle (`start`, `stop`,
`process` on a timer), and one engine kept for the life of the process (R3).
